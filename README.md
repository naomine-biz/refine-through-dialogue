# refine-through-dialogue

原案を、説明役と想定読者のポッドキャスト風の会話にしてから、文書として仕上げるスキルです。読者役が質問したり、自分の言葉で理解を確かめたりする場面を手がかりに、説明の不足を補い、読者が理解を進められる順序に整えます。

原案 → 読者役との会話 → 疑問と応答の点検 → 完成原稿

会話は推敲用の中間原稿として残します。会話で理解を助けた理由や具体例、説明の順序を、完成する本文へ戻します。詳しい手順は [SKILL.md](SKILL.md) にあります。

## 向いている場面

- 書き手には明らかな前提が、読者にも伝わっているか点検したい。
- 提案書や手順書で、理由・仕組み・担当者・条件を追いやすくしたい。
- 用語は説明したものの、読者が具体的な場面を思い浮かべられるか確かめたい。
- テーマはあるが原案がなく、対話で考えを整理するところから始めたい。

## 使い方

対象の原稿またはテーマ、想定読者、読後に理解・判断してほしいこと、保存先を伝えます。

原案がある場合の依頼例：

```text
$refine-through-dialogue を使って、docs/proposal.md を仕上げてください。
想定読者は、この提案を初めて読むチーム責任者です。
導入する理由、運用の流れ、判断が必要な条件を理解してほしいです。
会話ログは docs/proposal-dialogue.md に保存し、完成原稿は
docs/proposal.md に反映してください。
```

原案がない場合の依頼例：

```text
$refine-through-dialogue を使って、備品購入の申請手順を文書にしてください。
想定読者は新しく入ったメンバーです。
何を記入し、誰の承認を待つのか理解してほしいです。
まず私との対話で原案を作り、読者役との会話を経て仕上げてください。
保存先は docs/purchase-guide.md です。
```

会話ログがすでにあれば、原案との読み比べから始められます。「会話原稿だけ作って」と指定した場合は、その工程まで進めます。

## 効果の例

以下は、変化を示すための架空の例です。会話の人物と質問は生成したもので、実際の読者による評価や改善実績を示すものではありません。改稿には、各原案に書かれた情報を使っています。

### 例1：申請から発注までの順序と担当者がわかる

想定読者は、初めて備品を申請するメンバーです。原案には必要な情報がありますが、手順と担当者の説明が離れています。

**原案**

> 備品購入の申請はフォームに統一します。申請には品名・数量・希望日を記載します。承認後に総務が発注します。承認は所属チームの責任者が行います。記入漏れによる確認の往復を減らすため、3項目を必須にします。

**会話の抜粋**

> 読者役：フォームを送ったら、総務が発注してくれるんですか？
>
> 説明役：その前に、所属チームの責任者の承認が必要です。総務は承認後に発注します。
>
> 読者役：申請、チーム責任者の承認、総務の発注、という順番ですね。希望日も必ず書くんですか？
>
> 説明役：はい。品名・数量・希望日を必須にして、記入漏れによる確認の往復を減らします。

**改稿**

> 備品を購入するときは、申請フォームに品名・数量・希望日を記入してください。記入漏れによる確認の往復を減らすため、3項目すべてを必須にしています。
>
> 申請後は、所属チームの責任者が承認します。その承認を受けて、総務が発注します。

会話で出た「送信したら発注されるのか」という疑問を受けて、申請・承認・発注を順に説明しました。読者は、自分が記入する項目と、その後に誰が何をするかを続けて追えます。

### 例2：決まっていることと、まだ決める必要があることがわかる

想定読者は、案内ページの公開を判断する責任者です。原案には、公開前の確認と公開後の更新がまとめて書かれています。

**原案**

> よくある質問を案内ページにまとめ、問い合わせ件数を減らすことを目指します。公開前に窓口担当が内容を確認します。公開後も情報を更新しますが、更新担当と見直しの頻度は未決です。

**会話の抜粋**

> 読者役：窓口担当は、公開後の更新も受け持つんですか？
>
> 説明役：決まっているのは、公開前の内容確認です。公開後の更新担当と、見直しの頻度はまだ決まっていません。
>
> 読者役：では、公開後に誰が情報を見直すかは、別に決める必要がありますね。問い合わせが減ることも、もう確認できているんですか？
>
> 説明役：問い合わせ件数の削減は、この提案の目標です。原案には、効果を確認した実績は書かれていません。

**改稿**

> 問い合わせ件数を減らすことを目指し、よくある質問を案内ページにまとめます。公開前には、窓口担当が内容を確認します。
>
> 公開後も情報を更新する方針です。ただし、更新担当と見直しの頻度は未決で、今後決める必要があります。

会話で、公開前の確認担当と公開後の更新担当が区別されました。本文にもその区別と未決事項を残すことで、責任者が次に判断する論点を見つけやすくなります。問い合わせ件数の削減も、提案の目標として維持しています。

## 成果物と確認すること

文書の仕上げまで依頼した場合は、会話ログと完成原稿を保存し、改善した点と残る未決事項を伝えます。会話ログの保存先を指定しなければ、原案の隣に `<原案のstem>-dialogue.md` を置きます。

改稿では、次の点を確認します。

- 重要な主張や条件が、原案から失われていないか。
- 会話で解消した疑問への説明が、本文の必要な位置にあるか。
- 未決事項や未検証の条件が、確定事項に変わっていないか。

生成した会話の回答は、原案・既存資料・ユーザーの発言と照合します。読者役の反応は推敲の手がかりとして使い、新しい根拠やユーザーの決定として扱わないようにします。
